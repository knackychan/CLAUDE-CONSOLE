# Next step in the same task: design guideline

Status: **planned**, 2026-10-15. Implement with [Plan 36](../../plans/36-next-step/README.md).
This is the interaction and visual contract for that feature, not a redesign of the Console.

## 1. User job and success

Fred has just read an agent's reply and wants to move this specific task forward: keep talking,
ask another model to verify it, or start the next coding/investigation/planning session with the
work so far intact. The mode is **Operate**: make the next action obvious without making the
transcript or task history harder to read.

Success is visible: the same task gains step 02 beneath step 01; step 02 shows the chosen model,
starts in the same folder, and its Received tab explains what came from step 01. The user does
not copy/paste a transcript or recreate the task to change providers.

## 2. Visual authority and scope

Preserve `design/rework/locked/cells-board.html`, `cells-drawer.html`, BRAINSTORM 7.5 and the
current `web/style.css` tokens. The supplied screenshot confirms the actual Board context:
task chain at left, selected conversation at right, compact follow-up box below its last reply.
This feature extends that footer. Do not introduce a wizard, modal, separate workflow page,
large cards, decorative icons, gradients, or a new navigation layer.

Reuse `.askbox`, `.lr`, `.btn`, `.in`, the existing selects, fold/disclosure behavior, model
labels, status sprites and Chat/Received/Handoff/Route tabs. All CSS remains in style.css.
Use current UI font for forms and prose, mono for step numbers, routes and provenance. Doto
stays where the existing app uses it. No new palette, font, shadow or animation vocabulary.
Orange continues to mean needs-you, not a generic call to action. Use the existing neutral
primary treatment for Add next step and Start step; reserve red for failure, green for verified
results, and the existing working treatment for an active run.

## 3. Three distinct actions

| Label | User expectation | Result |
|---|---|---|
| Continue chat | More conversation with this agent | Existing session and context, no new step |
| Add next step | Another session to move this task forward | Fresh session, same task/folder, handover |
| Finish task | Done with this task | Existing finish behavior, history retained |

Keep Hand off as a secondary action when the server allows it. Its help text is
"Prepare a handoff for a separate task." Keep the existing post-handoff action with label
"Start new task" on this surface. Never label both same-task append and separate-task creation
"Start next chat". Do not make handoff mandatory before same-task append.

For eligible task sessions, any restored Verify shortcut opens Add next step with Verify
selected. It must not secretly invoke the old same-session Verify lever. Legacy loose sessions
remain outside this feature and retain their existing controls.

## 4. Footer and inline form

At the current chat's completed turn, keep the existing follow-up textarea. Place Continue chat
next to it as today; place Add next step and Finish task in the adjacent action row. Hand off
and any existing separate-task action are quieter secondary controls beneath that row when
applicable. The footer belongs inside the inspector scroll flow, not overlaid on the transcript.

When Add next step opens, replace the follow-up editing area with this inline form, preserving
the follow-up draft in memory. Never show two competing prompt textareas at once.

```text
Next step
From 01 Chat                 Same project: CONTENT MANAGER

Work          [Code v]       Model       [Auto v]
              Auto resolves to <actual model/provider>

Instructions
[The next concrete action, editable                         ]
[                                                          ]

> Handover from step 01                         <word count>
  Fresh session. Receives this handover, not the full chat.

[Start step]  [Cancel]
```

This diagram is a layout contract, not new styling. The project/model shown at runtime are
real metadata. If not resolved yet, display "Checking model...", not placeholder model names.

Form requirements:

- Work options in order: Code, Verify, Investigate, Plan, Chat. Stored kind mapping is in Plan 36.
- Model uses the existing configured model registry and labels, with provider shown when useful.
  Include Auto first. Do not present tier names as if they were exact model IDs. Unavailable
  configured choices can remain disabled with a reason; incompatible check providers are disabled.
- The resolved route is visible before Start. Verify may say "Fresh session, same model" if Auto
  cannot choose a different eligible model. Never promise an independent model without evidence.
- Instructions is a persistent labelled textarea, not placeholder-only. Seed from Next when usable;
  Verify has a concrete verification default. User edits win over rerenders and changing the model.
- Source step, project and kind remain visible even when the handover disclosure is closed.
- Handover disclosure shows the six existing sections, facts with their recorded time, source links,
  and omissions. Use the existing fold/heading grammar, not a new tab nested inside the form.
  Fallback copy: "Built from the last reply. Check the handover before starting."
- Editing the package itself is out of scope. Instructions can supplement it; refresh can rebuild it.
  The original task goal and saved handover remain inspectable and are not overwritten by instructions.
- The project is read-only here. Changing folders creates a different task through the composer.

## 5. State and copy contract

| State | What appears | Allowed behavior |
|---|---|---|
| Current turn running | Existing writing/Stop UI | No append launch; explain "Available when this turn finishes" |
| Replied and eligible | Follow-up plus next-step actions | Continue or open next-step form |
| Historical step | Its transcript and handover; "Next steps start from the latest step" | Link to latest, no append from this step |
| Form preparing | Inputs and local status "Preparing handover..." | Cancel; Start disabled |
| Ready | Source, route, instructions, handover disclosure | Start, Cancel |
| Missing required instructions | Field error "Describe what this step should do" | Keep draft; focus field |
| Model unavailable | Specific reason adjacent to Model | Choose another; never substitute silently |
| Source changed | "This step changed. Refresh the handover before starting." | Preserve instructions, refresh then Start |
| Starting | "Starting step 02..." and busy Start | Prevent double submit; do not show running prematurely |
| Held | Existing budget/Fable reason and confirmation control | Existing policy, no duplicate step |
| Launch failed | Specific error and Retry on the reserved step | Preserve handover and choice, same step on retry |
| New session running | Select its Chat tab in the same task | Older steps remain visible |
| Manual step complete | Result and next-step actions | No automatic Verify or Fix |
| Verify FAIL | Existing failure styling, findings retained | User chooses next action; no auto-edit |
| Agent request queued | "Verify with Astra queued after this turn" using real selection | Cancel until dispatch; show source |
| Agent request blocked | Specific interruption/question/hold/conflict reason | Existing recovery or next-step form |
| Task finished | Existing Done appearance | Explicit Add next step can reopen if eligible |

Do not put every disabled action in a permanent toolbar. Show the relevant action and a concise
reason near the user's attempted path. Source-step history must never look actionable merely
because its old session is idle. Task-state and run-state decisions come from the service.

Continue uses existing cold-cache confirmation if applicable. A fresh step consumes its handover
and does not reuse that confirmation wording. Do not claim it is free: a new model run still costs
usage, and any existing hold applies.

## 6. Selection, focus, drafts, and scrolling

- Opening the form focuses Work. Cancel restores the previous follow-up draft and focuses
  Add next step. Escape closes only this inline form before triggering the page's Back action.
- Keep next-step draft keyed by task and source step/session/revision during snapshot updates.
  A deliberate task switch must not send that draft to the newly selected task. Preserve it in
  memory for returning to the source; persisted cross-restart drafts are out of scope.
- Typing must not lose caret/focus when polling rerenders. No default selection of all text after
  every update. Enter in Instructions adds a newline; only Start submits. Do not bind a new
  global shortcut in this feature.
- Start keeps the task selection and selects the new step's Chat tab when the service confirms
  creation. Announce its state without forcing the scroll to the newest message while the user
  is reading history. Focus the new step heading once; ongoing streaming must not steal focus.
- Error messages stay beside the form, preserve values, and are exposed as status/alert text.
  A successful request with a held route is not a network error and must not recreate the form.
- Disclosure is a real keyboard-operable button with expanded state. All inputs have labels;
  tab order follows visual order; focus rings use existing tokens. Status cannot rely on color alone.

## 7. Responsive and motion rules

At the 900 px Board, source summary and the two selects may share rows within the inspector.
At 400 and 340 CSS px, stack Work and Model, wrap the action row, and allow long project/model
names to wrap without pushing controls outside the viewport. The textarea fills available width.
No horizontally scrolling form, fixed-width overlay, or second vertical scrollbar inside it.
Long handover content stays in the existing inspector scroll area.

Use existing density and spacing; do not enlarge the whole Board to accommodate this form.
Check 130% text scaling, dark/light themes, long instructions and absent/very long handovers.
Use normal in-flow expansion; no animation is required. If an existing transition is reused,
respect reduced motion and do not animate height while the user types or streams arrive.

## 8. Agent request experience

The agent and buttons create the same visible step. Tool access is Console orchestration, not
Claude subagent selection. A successful tool request while the source is live says it is queued;
the UI immediately shows kind, model and Cancel. It becomes a step only through the service's
accepted transition. When started, display its actual model/provider and source handover just as
for a button-created step. Never add an invisible job outside the task chain.

No automatic interpretation of every chat message, no model-name guessing, and no claiming
"Astra started" before the run exists. If bridge access is unavailable in that session, the agent
directs Fred to Add next step. Capability/configuration details stay out of normal product copy.

## 9. Design acceptance checklist

- [ ] Looking below the reply answers "continue this conversation or start another step?"
- [ ] Same-task append and separate-task handoff cannot be mistaken for each other.
- [ ] Source, folder, chosen work and resolved model are visible before Start.
- [ ] A missing structured handoff still has a truthful, inspectable fallback.
- [ ] New step appears in the same chain, with accurate route and Received information.
- [ ] Historical steps cannot launch or accidentally receive follow-up text.
- [ ] Typing survives snapshots; keyboard/focus and Cancel work without losing drafts.
- [ ] Every pending/error/held/queued state has precise copy and a recovery path.
- [ ] Layout passes 900/400/340 px, light/dark, text scaling and reduced motion.
- [ ] No new visual system, modal, wizard, provider settings page, or workflow-builder UI.

Review once with all target sizes/states using fake harnesses, fix the findings as a batch, and
confirm once. Record missing live validation separately; do not endlessly polish unrelated UI.
